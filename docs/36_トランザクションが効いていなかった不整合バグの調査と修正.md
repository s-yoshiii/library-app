# 36. トランザクションが効いていなかった不整合バグの調査と修正

## 今回起きたこと

`POST /loans`（書籍の貸出）を Insomnia で叩いたら、講座の動きと違って **「書籍の貸出に失敗しました。」（500エラー）** が返ってきた。

---

## 調査の流れ（再現の手順）

エラーメッセージだけでは原因がわからないので、以下の順で切り分けた。

1. **サーバーのログを直接見る**
   コントローラーは `catch` の中で `console.log(error)` しているので、ターミナル（`yarn dev` を実行している画面）に本当のエラーがそのまま出る。レスポンスの `{"error": "..."}` は表示用に固定文言にしているだけで、本当の原因はここには出ない。

   ```
   Error: 書籍はすでに貸出中です。
       at Book.loan (src/domain/entities/book.ts:26:13)
   ```

2. **DBを直接見る（sqlite3コマンド）**
   ```bash
   sqlite3 prisma/dev.db "select * from Loan where bookId='...';"
   sqlite3 prisma/dev.db "select * from Book where id='...';"
   ```
   結果：
   - `Loan` テーブルにはその本の貸出記録が **0件**
   - `Book` テーブルの `isAvailable` は **0（貸出中）**

   → 「貸出中」のフラグだけ立っていて、貸出記録がどこにもない。矛盾した状態でDBに保存されていた。

---

## なぜ矛盾が起きたか

[35番](35_リポジトリインターフェースへのctx引き渡し.md)で `ctx?: TransactionContextInterface` を各メソッドに追加したが、**実際にその `ctx` を使って分岐していたのは `PrismaBookRepository.create` だけ**だった。

```typescript
// 修正前の update（ctxを受け取っていない）
async update(book: Book): Promise<Book> {
  const updatedBook = await this.prisma.book.update({ ... });
  // ↑ 常に this.prisma（トランザクションの外側）で書き込んでいた
}
```

`LoanBookUseCase` 側はこういう流れになっていた。

```typescript
return await this.transactionManager.run(async (ctx) => {
  const book = await this.bookRepository.findById(bookId, ctx);
  book.loan();                                  // ① 在庫を「貸出中」にする
  await this.bookRepository.update(book, ctx);  // ② DBに保存 ← ctxを無視
  const newLoan = new Loan(...);
  const createLoan = await this.loanRepository.create(newLoan, ctx); // ③ 貸出記録を保存 ← ctxを無視
  return { ... };
});
```

`update` と `create` が `ctx` を無視して `this.prisma` で直接書き込んでいたため、②の時点で「貸出中」がそのままDBに確定してしまう。本来は `$transaction` の中で行われた処理は、コールバック全体が成功するまでコミットされないはずだが、`ctx`（トランザクション専用のクライアント）を使っていないので「トランザクションに参加していない、ただの別の書き込み」になっていた。

その後③で何らかの理由でエラーが起きても、②はもう確定済みなので元に戻らない。これが [34番](34_トランザクション管理の実装と型エラー修正.md)で説明した「トランザクションなしの問題」とまったく同じ状況。

---

## 修正内容

`PrismaBookRepository.findById` / `update` と `PrismaLoanRepository.create` / `findById` / `findByUserId` の全てに、`PrismaBookRepository.create` と同じパターンを適用した。

```typescript
async update(book: Book, ctx?: TransactionContextInterface): Promise<Book> {
  const prisma = ctx ? (ctx as PrismaClient) : this.prisma;
  const updatedBook = await prisma.book.update({ ... });
  ...
}
```

`ctx` が渡されていれば必ずそれを使う。これで `LoanBookUseCase` 内の全ての読み書きが、同じ1つのトランザクションの中で行われるようになった。

### 動作確認

1. 矛盾したテストデータ（`isAvailable = 0` だが `Loan` レコードなし）を `isAvailable = 1` に戻す
2. サーバーを再起動し、同じリクエストを2回送信
   - 1回目 → `201 Created`、`Loan` レコードが作られ、`Book.isAvailable` が `0` になる（整合性OK）
   - 2回目（同じ本） → `書籍はすでに貸出中です。`という **正しい業務エラー** が返る

---

## 今回の調査で使ったテクニック（メモ）

- **`console.log(error)` が出ている場所を探す**: APIのレスポンス文言は本当の原因を隠してしまうことが多い。サーバー側のログを必ず見る。
- **DBを直接クエリして「あるべき状態」と比較する**: コードを読むだけでなく、実際のデータがどうなっているかを見ると矛盾の証拠が掴める。
- **同じリクエストを複数回送って挙動の違いを見る**: 1回目と2回目で結果が変わる場合、「状態」が絡む不整合のヒントになることが多い。

---

## 今後の課題

- 今回 `ctx` を「渡されたら使う／渡されなければ`this.prisma`を使う」という分岐を各メソッドに手で書いたが、リポジトリが増えるたびに同じパターンを書く必要がある。共通化できないか今後検討する余地あり（今は学習中なので一旦このままで進める）。
